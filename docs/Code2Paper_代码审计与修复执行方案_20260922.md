## 0. 执行结论

当前分支不能再按 9 月 17 日的事故报告原样实施一次大修：事故归档之后，运行身份、单规划器选择、Writer 作者语义表面、Writer/Binder 分阶段验收、段落数分页、账本诊断、产物索引及离线检查均已有新增实现。应当保留这些有效改动，修复它们之间尚未闭合的生产路径，而不是再增加一套 V5 管线或平行账本。[S01] [S02] [S06] [S09] [S18]

**当前最重要的剩余问题不是文件名难看，而是“被验收的对象”和“实际执行的对象”仍可能不一致：**

1. 页编译器限制的是部分技术段落，而不一定是实际 Writer 请求中的全部段落。无 atom 的 header 页直接返回，混合章节的无 atom 段落又被跳过；实际输出 token 估量器也没有接入已核对的候选页判定点。[S11] [S12]
2. 运行身份已经分离引擎和目标仓库，但目标 dirty 身份仍使用不含文件内容的旧摘要；`fork_authoring → resume` 的创建模式与导入来源保存也存在明确冲突。[S03] [S04] [S05]
3. 目录准入、内容预算、发送侧拦截及崩溃恢复尚未使用同一状态归约规则。预发送拒绝、真实响应、传输异常、未结算请求不能继续靠事件序号和散落字符串混合判断。[S07] [S08] [S19]
4. 产物索引提供了方向正确的接口，但其 resolver 不复核当前文件字节，非法 JSON 可被记为 active，显式引用摘要未匹配时仍回退选最高 generation；不能直接把这个实现提升为生产真源。[S13]
5. 作者单元合并会丢失 `optional_details` 等字段；新槽位决策接口没有替换真实分配中的 `_best_slot`；验收失败码与新 repair packet 的失败码还不统一。[S09] [S10] [S15]
6. 当前指定的“离线端到端”测试关闭了正文写作，不能证明 Writer→下游绑定→正文交付已闭环。质量比较器还把部分不具备单调优劣关系的计数标成了 `better/worse`。[S17] [S20]

**执行原则：先补反例，再修现有 owner，再验证真实接线，最后做有界 live。任何历史目录都不得通过删除 attempt ledger、改写 accepted 回执或提高旧页预算来“变绿”。**

## 2. 当前流程：保留分层，收敛执行真源

下面表示数据和验收依赖，不把所有模块误画成彼此独立的生成管线。

```text
CLI / replay
  └─ 打开执行：输入身份 → new / resume / fork 准入 → run lease
       └─ Research 或经校验的冻结 Research 导入
            ├─ repo snapshot / source manifest / facts / claims / typed gaps
            └─ intent obligations / story spine / completeness / handoff
                 └─ mechanism contexts / evidence closures / unified archive
                      ├─ Formalizer worksets → formula obligations/packages/receipts
                      └─ 选择唯一 executable narrative planner
                           ├─ V4 intent plan → V3 执行投影
                           └─ 或显式 V3；shadow 不得成为第二个执行 owner
                                └─ 按输入闭包与输出任务修订物理分页
                                     └─ V2 compatibility adapter / Writer manifest
                                          └─ invocation plan / budget envelope
                                               └─ 最终实际 Writer request
                                                    └─ Writer content acceptance
                                                         ├─ bounded repair / typed research request
                                                         └─ Realizer 与 Binder 等下游回执
                                                              └─ final-bound acceptance
                                                                   └─ paragraph composition
                                                                        └─ candidate / verified / review
                                                                             └─ summary / doctor / quality
```

入口的 Research 主线在 `autonomous_method_agent.py` 中明确复用现有 research graph，而不是 R8 legacy bridge；replay 也已有“冻结 Research 权威输入”和“派生 authoring 输入”的复制边界。保留这些边界，不新增 Research2 或 Writer3。[S05] [S24]

### 2.1 五种对象不要再混为一个“版本”

| 对象 | 权威内容 | 允许变化的原因 | 不得承担的职责 |
|---|---|---|---|
| Research evidence | 实现事实、代码跨度、条件、来源闭包 | 新研究、源代码变更 | 不决定论文所有叙述顺序 |
| Semantic narrative plan | 作者主线、reader goal、叙述角色、内容义务 | 有记录的语义 replan | 不把作者陈述升级成代码证明 |
| Physical page plan | 页内段落、闭包、输入/输出预算 | 分页与受约束拆段 | 不删 required detail，不偷换段落权限 |
| Invocation contract | 对具体页面、请求、模型、规则和预算的绑定 | 明确的新执行契约 | 不复用另一个契约的 accepted 状态 |
| Artifact registry/snapshot | 哪一 phase 使用哪份不可变字节 | producer 发布新代 | 不从文件名、mtime 或最高数字猜真源 |

## 3. 剩余缺陷清单及最小反例

### F01 / P0：分页限制没有覆盖最终 Writer 合同

**源码确定行为。** `unified_context_compiler.py::_build_section_pages`（位于 `extend_writer_worksets_from_narrative_plan` 内）对 `not atom_ids` 直接构造一张 header page 返回；随后技术分组又对 `not group_atoms` 执行 `continue`，说明纯叙事段落不参与该组段数统计。候选页判定点只增加了 `len(set(candidate_paragraph_ids))` 上限，并未调用 `evaluate_page_contract`。[S11] [S12]

最小反例 A：一个合法章节包含 7 个必须保留的作者描述/动机段落，无技术 atom，单页候选上限为 6。当前 header 分支仍直接返回一页。最小反例 B：1 个有技术闭包的段落，加若干无 atom 但有真实作者语义的段落；技术组的段数不代表 adapter 最后装入请求的段数。

**禁止修法：** 删除无 atom 段落、给它们伪造 atom、把它们一律写成已验证实现、只把常量 6 改成 3，或者关闭段数检查。

**必修点：** 所有可写段落先进入同一个候选页构建器；atom 空只表示技术闭包为空，不表示没有叙事任务或输出成本。最终实际 request 构造后，再用同一段落集合执行一次确定性契约核对。后验核对只负责拒绝编译器遗漏，不允许在发送时偷偷改页。[S11]

### F02 / P0：目标仓库内容身份仍会漏变更

**源码确定行为。** `capture_target_identity` 调用旧 `dirty_manifest_digest`；该函数的 docstring 明确“不包含文件内容”，实际散列 `repo_root + git status --porcelain`。`build_run_open_identity` 又将 target HEAD 和该摘要放入名字像完整 snapshot/tree 的字段。[S03] [S04]

最小反例：同一目标文件已经处于 `M` 状态，从实现 A 改成 B，HEAD 与 porcelain 路径状态不变。新 V2 准入请求可能仍获得相同的目标代理身份；换目录又可能因 `repo_root` 改变而误拒绝完全相同的源内容。

这不是断言后续所有 Research 校验都失效，而是确认**打开 run 的身份判据本身不足**。不能用后续可能存在的更强校验替代“首次模型调用前”的身份冻结。

### F03 / P0：fork 恢复与锁内二次准入未闭合

`AuthoringExecutionIdentityV2.compatible_fields()` 包含创建模式和研究导入字段；`build_run_open_identity(run_open_mode='resume')` 却按非 fork 分支构造 `creation_mode='new'`。产品 `open_authoring_execution` 仅在本次 mode 为 fork 时计算 checkpoint 导入摘要，普通 resume 不会从既有身份恢复其出生信息。因此一个合法 fork 执行再 resume，存在 `creation_mode` 及导入来源不匹配的确定路径。[S03] [S05] [S25]

同时，当前 `open_authoring_execution` 的顺序是 `validate_run_open → acquire_run_lease → create_or_validate_execution_identity`，并没有在持锁后再次执行完整的目录/预算准入。并发进程若在预检后遇到另一进程已结束并留下相同身份的非空目录，后续 identity 校验不能替代 `new` 必须拒绝非空目录的规则。租约还由模块全局集合长期持有，产品函数的 finally 只恢复 signal handler；应测试长寿命进程中连续任务的释放行为。[S05]

### F04 / P0：账本的四个判断口径仍不一致

| 位置 | 当前判断 | 缺口 |
|---|---|---|
| `scan_exhausted_invocations` | 寻找历史 `attempt_limit_exhausted:*` completed 记录 | 两次真实失败但还没有第三次拒发时可能不报告；历史拒发也可能覆盖后续接受事实 |
| `read_invocation_ledger_state` | 主要读取 completed，按 `sent_to_caller` 统计发送/内容尝试 | 未完成事件、损坏 JSON、传输失败与可评价内容响应未统一处理 |
| `_capturing_writer_caller` | `attempt > limit and (content_exhausted or no_pre_send_rejection)` | 仍混入事件序号与历史拒发分支，不是单一内容状态机 |
| `read_attempt_outcomes` | 根据若干文件存在性分类 | attempt 集合只来自 started/completed；孤立 request/response 可能漏掉，某些缺响应的 completed 又被标为可回放 |

依据：[S07] [S08] [S19]。

**最小反例必须覆盖：** 两次真实失败且无拒发记录；只有 started；只有 request；只有 response；completed 存在但 response 缺失；损坏的 acceptance；历史拒发后出现同契约合法接受；超时但是否发送未知。每个场景只能有一个恢复结论，不能由 doctor、CLI 和发送包装器各自解释。

### F05 / P0（作为生产 reader 前）：索引不验证它声称冻结的字节

`authoring_artifact_index.py` 的确定行为包括：[S13]

- JSON 解析失败后 `payload=None`，文件仍可获得 `active` 状态。
- 显式 `reference_digests` 没有唯一匹配时，零匹配情况仍回退到最高 generation。
- `resolve_artifact` 不重新计算文件 bytes digest；`expected_digest` 只比较 index 缓存中的 semantic digest。
- `upstream_digests` 实际写入空字典；resolved snapshot 复制缓存摘要，而不是确认当下字节。
- 同 phase snapshot 写回固定文件名，允许覆盖；hardcoded 文件清单只认识有限代际。

最小反例：建立索引后改动 active JSON 的内容，再 resolve，不要求指定额外 expected digest；当前 helper 仍返回该路径。另一个反例是传入一个不存在的显式上游 digest，build 仍选择高代文件。

**范围限定：** 这证明新索引 helper 不满足可靠读取契约，不等于断言整个系统已经由此发布了坏正文。产品 `_writer_artifact_paths` 已有“只接受本 revision 的 persisted_paths，legacy discovery 需显式启用”的保护，不能在索引迁移时把它拆掉。[S05] [S13]

### F06 / P1：单元合并丢信息，绑定决策未进入真实分配

`compile_authoring_units` 合并同类非 grounded 单元时，合并了 story、slot、surface、部分义务，但没有合并 `optional_details`、formula obligation 集合和不同 reader goal 的处置。两个同类 author-specification 槽位各带一个 optional detail，可以合并成一个 unit，却只剩第一个 optional detail。[S09]

此外 `_slot_binding_decision` 已能输出 overlap/status/needs_research，但实际 detail、package 与 argument unit 分配仍使用 `_best_slot`；零重叠被记录为 fallback，并未通过新决策对象驱动后续路由。不能因为一个 decision dataclass 已经存在，就认为错误叙事归属已被阻断。[S09] [S10]

### F07 / P1：语义摘要、权限和输入消费字段需一起守恒

`_story_intent_payload` 未包含被 surface 编译使用的 `reader_question`；修改该局部 reader goal 不会改变这一特定意图摘要。`compile_authoring_units` 对 surface 使用 `model_copy(update={'implementation_status': ...})`，而 surface 的 digest 在 model validator 中生成：必须验证修改后的内存对象与序列化再载入对象是否同摘要，不能依赖某次下游再验证偶然补正。[S09] [S16]

这里不宜立刻把整个 run 视为身份失效：入口还对作者输入文件做字节散列。真正要修的是不同层级的局部 digest 自洽，否则页身份、复用、回放和“同输入”指标会表达不同内容。

### F08 / P1：验收与修复失败码不统一

当前 transaction 的测试使用 `detail_witness_missing`；`writer_repair_packet.py::_REPAIRABLE_EDITS` 使用 `missing_detail_witness`。把前者直接传给新 packet builder 时，会落入默认 `('paragraph_content',)`，而不是显式的正文与 detail witness 双修复路径。`paragraph_missing`/`missing_paragraph` 等也应逐项核对，不能再添加另一批反向同义字符串。[S14] [S15]

此外，`input_material_missing` 当前被归为原地补写，这不能自动解决缺失证据；权限/归属错误应交 Planner/Research，格式或局部内容不足才交 Writer。对未知 failure code 默认允许改正文不够保守，应返回“未知 owner/不可自动 repair”。

### F09 / P1：输出估量没有覆盖实际输出结构

`writer_output_workload.py` 计算了 `writer_owned_witness_count`，却没有将它独立计入估量总量；估量主要依赖 reader goal/作者 statement 的长度、detail 数及若干固定开销，而不是最终 serialized response 的 witness spans、公式引用和 prose 内容需求。任意非空 calibrated_profile 都能将 confidence 改为 calibrated。[S12]

最小反例：保持段数、detail 数和 goal 不变，大幅增加合法的 Writer-owned witness target 或其需要的 exact span 长度；输出负担增加，但估量不相应变化。第二个反例：传入仅含无关键的 profile，也不应该宣称已经标定。

固定 6 段只能保留为临时保守策略。不能从一个任务中的“最大成功页段数”推导跨模型、跨语言、跨输出协议的稳定成功概率。

### F10 / P1：单正文 helper 不等于出版物已经使用单正文

`paragraph_prose_composer.py` 建立了段落对象唯一正文源，方向正确；但 `normalize_writer_section_payload` 返回带 `prose_audit.valid` 的对象，并不会自行拒绝失效响应。生产验收必须明确读取该结果。其当前排序基于 ID 的自然序，而不是显式冻结的 paragraph order；在计划确实允许不同顺序时，不应让 composer 擅自重排。[S26]

本项首先是接线与契约测试任务，不把“helper 有缺省返回”直接说成整个发布门已放行。正文对象到 final-bound、formula splice、section composition、candidate writer 的实际调用要用 spy/fixture 跟踪。

### F11 / P1：离线准入和“端到端通过”证明范围不足

当前离线端到端测试明确关闭写作；它能证明身份和报告写入、重复打开规则、无假正文，但不能证明接受的 Writer 内容真的经过 Realizer/Binder、正文重建与发布。[S17]

`preflight_live_admission` 还允许未提供 runtime probe 仅告警；offline receipt 匹配主要依赖 passed 和引擎指纹。此类报告可用于离线准备，但不应被描述为已经具备实际部署、完整必测套件和正文通路的 live 证明。[S27]

### F12 / P1：质量比较的方向定义会奖励错误行为

`authoring_quality_comparison.py::METRIC_POLARITY` 将 formula.required 标成越少越好，must-cover 义务数标成越多越好，provider sends/tokens 标成越少越好，explicit gaps 标成越少越好。脱离固定义务集合与有效交付范围，这些方向并不成立：删义务、提前失败、隐藏 gap 都可能产生“改善”。分页后 accepted page 数增加也不意味着内容质量变好。[S20]

必须改成“同目标集合、同评价 scope、交付与覆盖不退化条件下”的效率比较。原始计数保留，但默认 direction=unknown；不能以机器指标替代论文连贯性与事实忠实度。

## 4. 修复后必须保持的不变量

这些是不变量，不是要求增加十套新门禁。应当复用已有验证 owner，并让多个调用方消费同一结果。

| 编号 | 不变量 | 负责边界 |
|---|---|---|
| I1 | Author intent 只能授权叙事与有界作者描述，不能凭空证明代码实现 | Intent compiler / authority validation |
| I2 | 同一执行只存在一个 executable semantic plan；未知配置不能静默选另一条主线 | 入口配置与 planner selection |
| I3 | 每个 required 内容义务有唯一主归属或显式跨段引用；重分页不减少义务 | Narrative/page compiler |
| I4 | 技术闭包按内容守恒；共享 atom 可跨页重复，但不能借此重复计算成果 | Unified archive/workset |
| I5 | 实际请求的段落集合、顺序、权限、公式引用与冻结 page contract 一致 | Request builder / pre-send |
| I6 | Writer 接受不等于 final-bound 接受；Binder/最终语义门缺失即不发布 | Writer / Binder / publication |
| I7 | Transport 未知结果不能自动当作未发送，也不能无界重新调用 | Invocation ledger |
| I8 | 历史产物和回执不改写；新规则重验要生成独立结果 | Replay / artifact registry |

| I10 | 完成率和效率不能通过删任务、缩小 scope 或隐藏失败提高 | Quality/reporting |

## 6. PR A：运行身份与 new/resume/fork 语义

### A.1 修改 `authoring_execution_identity.py`

**保留：** `AuthoringExecutionIdentityV2` 的引擎/目标/作者输入分离、已有 engine 内容指纹和明确拒绝码。**修改：** 不再用 target HEAD/porcelain 替代目标 source snapshot 的内容身份。[S03] [S04]

目标输入应复用现有 `repo_snapshot` 与 source manifest 的文件选择规则。不要另写一套“扫描整个目录”的目标快照：它容易把运行产物、缓存和无关数据计入目标身份，也会与 Research 真正读的文件集合不一致。

实施步骤：

1. 在准入前构建/读取可验证的目标 source snapshot，获得其实际内容摘要、project tree hash 和 source manifest digest。字段以当前 `RepoSnapshot` 类型为准，不能继续把 commit SHA 塞进名为 snapshot digest 的字段。
2. 将 target commit 保留为诊断字段；内容身份必须覆盖被纳入 Research 范围的未提交源文件、删除和新增内容。
3. 将路径保留为诊断信息，不纳入“相同内容是否可复用”的核心判断；跨目录移动仍要重新验证路径约束和实际字节。
4. 引擎及目标快照标记 missing/unstable 时，在任何新模型发送前停止。哈希失败不能通过“错误状态也有一个 sha256 字符串”伪装成可用身份。
5. `capture_validator_bundle_snapshot` 的 `failure_code` 必须被 `build_run_open_identity`/live 准入消费；非空 digest 不等于可用 bundle。
6. 将实际生效的 narrative mode、authoring context mode、输出协议、预算配置、prompt/schema/tokenizer 身份冻结进有效配置。未知 narrative mode 不得静默回退 V3。

**避免循环依赖：** 在启动时冻结引擎、目标、作者材料和有效配置；计划与页面尚未产生时，不要求初始身份包含它们。计划生成后，由阶段快照和 invocation contract 绑定 plan/page/validator digest。不要为了加入 plan digest 反过来先运行未准入的 planner。

### A.2 区分“本次打开动作”与“执行的出生信息”

`run_open_mode` 是本次动作；`creation_mode`、`parent_execution_id`、`research_import_digest` 是不可变来源。resume 不应重新发明它们。[S03] [S25]

建议修改 `build_run_open_identity` 的调用方式，接收经过严格读取的 existing identity 或独立的 birth metadata。以下为**拟修改接口的伪代码，不是当前已有 API**：

```python
existing = load_and_validate_existing_identity(out_root)  # 不猜测 legacy
birth = (
    existing.birth_metadata
    if requested_mode in {"resume", "auto"} and existing is not None
    else build_birth_metadata(requested_mode, verified_research_import)
)
expected = build_identity_from_current_inputs(
    birth=birth,
    engine=verified_engine_snapshot,
    target=verified_target_snapshot,
    effective_config=effective_config,
)
```

resume 的比较必须既防止输入变化，又允许“同一个 fork 执行以 resume 动作继续”。旧版本没有完整身份时仍拒绝原地 resume；显式 fork 到新目录才是迁移路径。

### A.3 修改 `autonomous_method_agent.py::open_authoring_execution`

当前预检后才取 lease，而完整准入没有在锁内重做。[S05] 改为：

```text
只读预检，尽早返回明显错误
    → 获取 out_root 的单写者 lease
    → 在锁内重新读取现有身份、目录状态和相关账本
    → 重新判断 new / resume / fork
    → create-or-validate，不覆盖已有身份
    → 执行入口持有 lease
    → finally 释放 lease
```

约束：`new` 若锁内发现业务产物已存在，即使 identity 相同也必须拒绝。调用异常、预检失败和长寿命进程中的下一次任务都不能泄漏 lease。进程内的 lease 幂等复用要验证 owner/execution 一致，而不是只要 root 相同就返回。

“拒绝零写入”的工程定义应明确：不写入业务身份/Research/Writer 产物；允许独立锁元数据或相邻 refusal 诊断，但不能先创建一批业务目录再声称没有影响旧 run。

### A.4 Research 导入应验证闭包，而不是只验证 checkpoint 外壳

`verify_research_import` 当前对 metadata 的检查不能替代 referenced artifact 的可用性、路径安全与内容一致性。replay 已有 traversal-safe、digest-pinned 的复制方向，应复用和前移这些规则，不另造一份 relaxed importer。[S03] [S24]

fork 可导入的内容是验证过的 Research 权威材料及其 provenance。默认不得继承 Writer attempts、content-acceptance、Binder 回执、旧 candidate、旧 invocation budget 或旧 active 指针。`execute-prepared` 若显式复用 Formalizer 产物，必须验证其完整依赖和兼容性，不能因文件名一致就认定准备完成。

### A.5 必须新增的测试

```text

 test_same_target_content_in_another_path_has_same_content_identity
 test_fork_authoring_can_resume_without_changing_birth_metadata
```

## 7. PR B：统一账本和可恢复执行

### B.1 保留一套持久记录，把多种 reader 收敛成一个 reducer

继续由现有 `unified_invocation_ledger.py` 持久化 request/response/acceptance 等事件；扩展 `writer_attempt_ledger.py` 为统一只读状态归约层。`scan_exhausted_invocations`、doctor、CLI、resume preflight 和 `_capturing_writer_caller` 必须消费相同状态对象，不得各自 glob 后判断字符串。[S07] [S08] [S19]

不要新建平行 SQLite、第二份“真正账本”或自动重置脚本。旧格式通过明确的只读 adapter 转成统一事件；adapter 无法确定的字段保持 unknown。

### B.2 计数语义先写清，再修改发送侧

| 量 | 增长条件 | 不增长条件 |
|---|---|---|
| event sequence | 记录一条新的持久事件 | 不作为内容重试上限 |
| provider-call attempt | 进入发送边界；未知发送结果需保守占用调用预留 | 纯 pre-send 拒绝 |
| received-content attempt | 收到可归属本次请求的模型响应；解析/内容无效也计入 | 明确未发送的失败、只有本地拒发诊断 |
| content repair | 在有可评价失败响应后创建、批准并发送修复请求 | 429/连接失败等传输重试 |
| accepted response | 同契约响应经过对应版本验收并落盘 | 只存在文件名、旧契约接受、未解析 acceptance |
| unknown reservation | 已可能发送但结果未能确定 | 已有确证未发送或已完成对账 |

上表是拟统一的预算语义。若保留现有字段 `content_attempts` 的旧含义，必须通过版本化转换或明确改名消除歧义；不能只改字段解释而不改预算消耗与测试。

全 run 调用数和 token 上界必须同时约束正常、repair、transport 重试及 callback。未知 usage 保留估计/预留及其 provenance，不填成“真实 0 tokens”。

### B.3 统一恢复状态表

| 已落盘材料 | 恢复状态 | 允许动作 | 禁止动作 |
|---|---|---|---|
| 仅 started，确认没有进入发送边界 | `reserved_not_sent` | 释放/回收预留并留下审计事件 | 当成一次内容失败 |
| request 已持久化，是否发送不可确定 | `send_outcome_unknown` | 优先对账；无可用对账能力则阻断自动重发 | 直接认定未发送、获得免费重试 |
| response 已持久化，无 completed | `response_received_unsettled` | 验证 request/response 摘要后本地结算 | 再请求同一份正文 |
| completed 存在，无 response 且无可靠引用 | `response_missing_or_ledger_inconsistent` | 保守阻断并给恢复原因 | 宣称可离线回放 |
| response 有效，无 acceptance | `validation_pending` | 对同契约做本地验收并落盘 | 把缺失 acceptance 当接受 |
| acceptance JSON 损坏/摘要冲突 | `ledger_corrupt` | typed block | 忽略文件后重新获得预算 |
| accepted 与当前契约完全匹配 | `accepted_reusable` | 直接使用该接受版本 | 被历史拒发事件永久覆盖 |
| 内容尝试已满且仍未接受 | `content_budget_exhausted` | 汇总主要失败并停止 | 同 root 加 attempt 编号继续试 |

**边界说明：** request 文件存在并不在逻辑上证明远端已经接收，因此要保存“未知”，而不是伪造确定结论。默认不假设服务具备按 request ID 对账或幂等去重能力。

### B.4 修改具体调用点

- `writer_attempt_ledger.py::_attempt_records/read_attempt_outcomes`：从所有已定义事件文件的并集构造 attempt 集合；严格解析，路径/标识精确匹配；禁止 substring 选第一目录。
- `read_invocation_ledger_state`：验收绑定 execution、plan、request、response、validator；损坏文件产生结构化阻断，不能 silently continue。
- `authoring_execution_identity.py::scan_exhausted_invocations`：改成上述 reducer 的薄包装，并按当前 required invocation 集合汇总，不被无关历史目录影响。
- `_capturing_writer_caller`：用归约后的预算和 reservation 状态判断；删除“事件号超限且存在/不存在拒发”的混合条件。
- `transport_retry_policy.py`：只产生 typed disposition，由同一个预算 owner 消费；不要在另一层独立重试导致乘法式重试。
- `authoring_doctor.py` 与 run summary：给出第一原因、scope、used/limit、unknown reservation、下游未运行阶段；`acceptance_count:0` 只能是结果，不再是唯一根因。

### B.5 接受、修复和崩溃后的幂等性

本地重验不得改写旧 acceptance 文件。若只是缺失结算，在相同契约下完成尚未完成的事件；若 validator 或代码身份变化，生成新的 validation replay 结果并记录 source response，不能把它冒充历史 run 当时就已接受。

每个阶段只有一个可用于下游的 active accepted response；历史 repair 候选仍保留。采用“响应不可变 + 接受引用原子提交”，避免先覆盖正文再发现修复不合法。

### B.6 必测矩阵

至少为上表每行建立一个离线反例，并增加：两次真实拒绝后没有 attempt-0003；两次纯拒发但零模型发送；accepted 后目录残留拒发记录；同名页不同 validator；response 写入后进程中断；Binder 前中断。对于所有场景，CLI、doctor、resume 和发送包装器的 `primary_cause` 必须一致。

## 8. PR C：以最终请求为对象的联合分页

### C.1 修改 `extend_writer_worksets_from_narrative_plan`

当前位于约 2630–2930 行的 header 提前返回、无 atom 段落跳过和候选页判断是首要修改点；使用冻结源码中的函数名定位，避免后续行号漂移。[S11]

把每个可写段落转换成一个统一的 packing unit，至少携带：

```text
paragraph_id + explicit narrative order
paragraph_kind + authority surface + implementation status
page-local author surfaces / reader goal
required & optional detail occurrences
Writer-owned witness obligations
formula packages + source-detail dependency closure
technical atom closure（可以为空）
```

这是对现有段落 row 的统一使用，不要求再生成一份平行的语义计划。`structural_only` 不产生正文，但必须有 coverage/disposition；`author_specification/expository_bridge/unresolved` 只要计划要求输出，就和 grounded 段落一样参与分页。

### C.2 统一候选页判定

候选页使用同一 `evaluate_page_contract`，至少有三类限制：

```text
完整输入请求 ≤ 角色单次输入上限
完整输入 + 输出预留 + 尚未计入的模板/推理/安全余量 ≤ 模型上下文
预计序列化输出 + 输出安全余量 ≤ 实际 provider completion 上限
```

输入计量已经包含的模板/schema/wrapper 不得重复相加；用字段定义和测试明确每一项只计一次。若 provider 把 reasoning tokens 算入 completion 上限，必须在该 profile 中显式处理，不默认这些 tokens 免费。

段落数上限可作为辅助安全限制，但不能替代 token 和义务估量。0=关闭上限只能作为显式实验配置；生产准入必须标注该策略，不接受环境变量悄悄改变契约。

### C.3 修正 `estimate_writer_output_workload`

建议沿用当前结果类型，补齐其估量来源与标定元数据，而不是新增另一套 budget schema。[S12]

- 使用实际输出 schema 构造最小响应骨架并计量：段落 ID、必需列表、formula placeholder、witness 对象、转义字符均有成本。
- prose 预算按段落任务的目标深度及材料量估量，不以 reader goal 字符数替代全部正文成本。
- Writer-owned witness 按 occurrence 与预期 span 长度计量；Binder-owned atom 元数据不要求模型重复输出，但底层技术材料仍必须可见。
- Formula obligation 与 package 不应无条件双计同一输出引用；需要明确“义务”与“实际 placeholder 数”的映射。
- calibrated profile 必须有匹配的 model、tokenizer、schema/prompt 标识、样本范围和估量方法；未知键或仅存在非空字典不能升级 confidence。
- 缺少可靠 tokenizer 时允许保守估量用于离线规划，但报告为 uncalibrated；live 的准入与风险策略必须显式，不能假装精确。

输出估量是规划工具，不是“足够 tokens 就一定生成正确”的证明。结构补齐、语义验证和生成失败仍由各自 owner 处理。

### C.4 页重组与段落拆分分开处理

优先将完整段落换页；只有单个段落自己的合法闭包仍超预算，才调用 `fit_narrative_plan_to_page_budget` 做受约束拆段。[S11]

拆分单位应尊重 formula-package/source-detail 的不可分依赖。不能把一个公式引用放在一页、唯一解释/授权它的 required detail 放在另一页，然后靠全局“曾出现过”过门。共享证据可以按页重复提供；主要内容义务的归属要明确。

拆段后必须记录 parent paragraph、fragment order 和义务映射，验证：

```text
required occurrence 集合：拆分前 == 拆分后
每个 required occurrence：有且仅有一个 primary owner
允许的 shared reference：有显式关系，不升级为额外完成量
formula consumer/source closure：仍完整
作者目标与权限：保持，或有明确计划修订记录
```

单个不可分单元仍超限时，返回说明真实限制维度的 typed failure。现在的 `ATOMIC_PAGE_OVER_BUDGET` 文案不能在“段落数超限”时只打印一个其实未超的 input token 不等式。

### C.5 同时重建 invocation 和剩余预算

重分页改变实际调用数、重复输入成本、repair lookahead 和 page ID，不能只改 manifest。重建本 revision 的 worksets、invocation plan、budget reservation、admission 和 phase snapshot；所有摘要引用必须指向同一代。[S11] [S12]

若是运行内授权的语义/证据修订，可以建立新的 stage generation，但保留全 run 已花费和未知预留，不能通过换 page ID 获得无限新预算。引擎修复或不兼容规则变更则使用新执行/fork，不在旧目录悄悄更换身份。

### C.6 最终实际 request 再核对一次

在 `_capturing_writer_caller` 之前，用最终 `LLMRequest` 的真实 `input_payload` 检查：

```text
实际段落 ID 和顺序 == 冻结 page contract
实际作者 surface 摘要 == 冻结 surface 摘要
实际技术材料摘要 == 本页的技术字节摘要
实际 formula/detail/authority scope == 本页合同
实际输出上限 == 本页估量使用的上限
最终请求 token accounting fits == true
```

这是对 compiler/adapter 漏项的保护，不是第三套规划器。若 adapter 后来又追加 15 段，这个边界必须在发送前明确拒绝为 `actual_page_contract_mismatch`，不能消耗一次 content repair。

### C.7 新增行为测试

```text
7 个无 atom 作者段落 → 按冻结策略分页，而不是一张 header 页
1 个 grounded + 15 个有材料的 narrative-only 段落 → 最终请求也满足上限
两个段落共享 detail → 允许证据重复，内容义务不丢不乱计
一个公式依赖多个 detail → 不切断公式授权闭包
witness 输出负担增大 → 估量必须增加
实际 provider 输出 cap 降低 → 重编译/阻断，不能沿用旧页
重分页后总调用预算不够 → 明确失败，不截断剩余页面
adapter 追加段落 → pre-send 拒绝，provider send 增量为 0
```

## 9. PR D：信息保真与语义归属

### D.1 修正 `compile_authoring_units` 的 merge

最小安全修复不是无条件把更多字段拼接，而是先收紧可合并条件：同一 section、同一权限与 implementation status、兼容的局部 reader goal、相邻位置，且没有禁止合并的 argument/intent 锚点。[S09]

对允许合并的单元，逐字段定义规则：

| 字段 | 合并规则 |
|---|---|
| story_ids / slot_ids | 保序去重，保留 provenance |
| surfaces | 按 surface ID 与内容摘要一致性合并；同 ID 不同内容报冲突 |
| required/optional details | 按 canonical ID 与内容摘要保序合并，不允许静默丢弃 |
| formula obligations/packages | 按义务与 consumer 关系合并，冲突则不合并 |
| local reader goal / status / authority | 不同且无法明确统一时，不合并 |
| unresolved IDs / disposition | 不因合并消失；保留每项的真实处置 |

如果 optional detail 被主动舍弃，应在 trace 中记录源 ID、原因与去向。optional 不等于“任何转换都可静默删除”；它也可能是改善正文的有用信息。

### D.2 把 `_slot_binding_decision` 接入实际 owner 选择

替换 detail/package/argument unit 分配中的直接 `_best_slot` 使用。零 overlap 的组织落位不提供语义授权：

- 有准确证据及叙事关联：正常 grounded placement。
- 代码事实有支持，但与当前作者槽位的关系不确定：保持事实证据等级，单独标注叙事关联不确定；交有界 Planner/Research 处理，不能强行让 Writer 把它当成本段主张。
- required 义务找不到合理归属：形成 typed gap/replan request；不得随便塞到第一段来满足 coverage。
- optional 材料无合理归属：保留在 review/候选上下文及 trace 中，不强制进入 clean prose。

不得把“组织 fallback”误写成“证据完全缺失”：叙事适配与代码支持是两条轴，应分别保存。

### D.3 修正局部指纹与模型更新

把实际消费的 `reader_question` 等语义字段纳入相应 content digest。已有入口文件字节摘要仍保留，不拿它替代局部 surface 摘要。[S09] [S16]

更新 sealed model 时使用重建并验证的路径，而不是带着旧 digest 的 `model_copy(update=...)`。例如在现有模型语义下可以采用：

```python
payload = surface.model_dump(mode="json", exclude={"content_digest"})
payload["implementation_status"] = implementation_status
updated_surface = AuthorIntentSurfaceV1.model_validate(payload)
```

必须测试 `object → JSON → model_validate` 前后各级 digest 相同，且只改 reader goal/status 时相关 digest 变化。严格读取历史产物时，应区分“验证 supplied digest”与“重新生成 digest”，不能悄悄修正旧文件再说它一直有效。

### D.4 核对最终 Writer 可见字段，而不是只看上游模型

对 `_compact_writer_narrative_plan_for_llm` 和 `_compact_writer_author_intent_surfaces_for_llm` 建立 golden contract：完整局部 statement、reader goal、authority、implementation status、支持 detail、unresolved disposition 必须按权限到达模型；技术事实继续来自 canonical page，不再复制一份可能不一致的“精简事实”。[S06]

不要把整份作者 brief 塞给每页。目标是按页提供足够材料，而不是让全局愿景诱导本页补写实现细节。对每个 required paragraph 保存来源到最终请求字段的 lineage，能够回答“材料是未检索到，还是在投影/合并中丢了”。

## 10. PR E：失败归属、修复事务与单一正文

### E.1 一个 canonical failure code 集合

在现有 `publication_transaction_contract.py` 中统一 code 与 `repairable_by`；新 repair packet 不再用另一套同义词。历史字符串只在 `contract_failures_from_legacy_strings` 读取边界转换。[S14] [S15]

| 失败类别 | 应接收的 owner | 允许动作 |
|---|---|---|
| detail witness 缺失，但证据与正文任务完整 | Writer | 只补失败段内容/引用跨度 |
| 缺段落，但该段材料和归属完整 | Writer | 补该段，不重写其他已接受段 |
| formula placeholder 缺失，但 consumer 正确 | Writer | 补合法引用，不自行改公式 |
| formula consumer/source closure 不一致 | Planner/Formalizer/Compiler | 修契约与依赖；不硬写过门 |
| input material missing | Research/Compiler | 补材料或标 gap，之后再编译 |
| authority 或 target scope 越界 | Planner/Research | replan/修授权，不原地捏造 |
| atom 绑定失败 | Binder 或按原因转回 Writer | 区分文本实际缺义务与纯绑定未完成 |
| transport 失败或结果未知 | Execution owner | 对账/有界传输处理，不花内容 repair |
| 未知失败码、账本损坏 | System | typed block，不默认允许改正文 |

多个 failure 同时出现时按责任和依赖选择动作，不能只用 `codes[0]` 决定整个 repair_kind。升级类失败优先，未知类不应降级成默认 prose edit。

### E.2 让修复包携带可执行的局部合同

现有 `WriterRepairPacketV1` 可继续使用，但调用边界必须真正消费它。packet 至少应可定位失败段、缺失 target、修复前正文、局部材料/证据引用、允许修改集合、其余已接受段的冻结摘要。

`as_request_payload` 可以隐藏内部 digest，但不能把修复必需的局部内容也一起丢掉；若这些内容在 request 的其他字段提供，测试必须验证组合后的真实 request，而不是只检查 packet 对象存在。

### E.3 原子提交和单调进展

接收 repair 后：验证其段落 scope → 验证冻结的其他段未变 → 用同一 transaction assessor 验证新增/保留义务 → 形成新的候选 response → 原子提交接受引用。

“单调”指已经满足的 required 内容、权限及证据约束不退化，不只是 rendered IDs 变多。结构补齐但加入新 unsupported claim，不能算进展。修复无收益时立即停止当前内容重试，不继续同内容循环。

### E.4 保留 Writer/Binder 的正确分工

`writer_content` 允许 Writer 不枚举 Binder-owned atom，但 detail/公式/正文义务仍需成立；`final_bound` 必须验证完整绑定及条件、极性、接口关系。前者是内容阶段接受，不是 publication acceptance。[S14]

负例必须包含：加了目标 ID 但没有相应正文；exact_text 不在段中；argmax 写成 argmin；比较方向反转；训练条件写成无条件推理行为；维度/归一化轴错误；两个相似 operation 串错来源。不能让词汇重叠代替关系正确性。

### E.5 让 paragraph objects 成为唯一正文源

生产实际接收路径调用 `normalize_writer_section_payload` 或等效现有 composer，且必须消费 audit 结果。required IDs 来自冻结计划，不以模型返回集合自证完整。[S26]

段落顺序以 plan 的显式顺序为准；自然数字排序只能是有明确定义的 legacy adapter。规则层允许做确定性拼接、授权公式块替换和纯结构标题处理，不能自行撰写新的过渡/机制解释。

公式插入后、Binder 绑定后和最终正文写入前，要确保所验证文本摘要与实际发布字节相符。历史 `section_markdown` 仅作为归档字段，不再与 `paragraph_markdown` 竞争正文真源。

## 11. PR F：阶段产物索引与不可变消费

### F.1 不从扫描器猜当前生产对象

保留当前产品的 `persisted_paths` 当前 revision 约束，producer 发布时向索引注册真实角色、phase、generation、schema、字节摘要、语义摘要和 upstream refs。[S05] [S13]

`_KNOWN_ARTIFACTS` 保留为 legacy 只读导入规则，不能继续作为生产“所有可能当前对象”的穷举表。新 generation 不应靠再写一个 `.writer.3` 分支才能被识别。

### F.2 修改 `build_artifact_index/resolve_artifact`

必须实现以下具体规则：

```text
非法 JSON / 不受支持 schema / 错误 semantic digest → invalid，不进入 active
显式 expected upstream digest → 必须唯一命中；零命中不得 fallback
同 role+phase 的多个未消歧候选 → ambiguous，不能选最高数字
active 路径必须对应相同 role+phase 的完整 entry
消费时读真实 bytes 并重算 file_bytes_digest
若带 semantic digest，使用 producer 的规范化规则复算并比较 supplied digest
路径越界/不允许的符号链接/依赖不完整 → typed block
```

读取 bytes 后应把同一份已验证字节交给 decoder，避免“验证路径后又重新打开另一份内容”。若为了兼容暂时保留返回 `Path` 的 `resolve_artifact`，新增受控的 validated-read 包装并迁移生产 consumer；不能声称 Path 本身已冻结内容。

### F.3 明确 valid_empty 的语义

Formalizer 无公式任务时，合法空 manifest 不应阻断整条主线。Writer 需要实现正文时，空 workset 是否合法取决于该阶段冻结的 required units，而不是所有 phase 共用 `allow_empty=True`。空对象也应记录为什么为空、哪些任务为 not_applicable。

### F.4 阶段快照不能覆盖

在阶段开始时冻结 `(role, phase, generation, input bytes digest)`。建议现有 snapshot 文件名带 generation 或 snapshot digest；固定名称只作为显式指针，不作为可覆盖的历史证据。相同快照重复写入可幂等，已有同名但不同内容必须拒绝。

发布流程：写产物临时文件 → 严格验证 → 原子发布不可变产物 → 注册索引 revision → 原子更新 active 引用 → 冻结阶段消费快照。某一步中断时，只能留 orphan/incomplete 状态，不允许 active 指向半成品。

不要增加新的全局数据库、人工填写哈希表或需要操作员手动同步的 current.txt。摘要由已有序列化/持久化边界自动生成。

### F.5 reader 迁移清单

实施时用本地代码搜索列出并逐项迁移：主 writer、Realizer、Binder、replay、doctor、quality report、run summary 以及任何“按无后缀 JSON 读取”的入口。正常路径禁止隐式 fallback；仅历史归档读取可以启用有名称的 legacy resolver，并在报告里标注。

每个已迁移 reader 需要一个变异测试：索引发布后改动文件，reader 必须在使用内容前失败。只测 index builder 本身不够。

直接修改 `authoring_quality_comparison.py::METRIC_POLARITY/_flatten/compare_authoring_quality_reports`，无需新增总分。[S20]

| 指标 | 修复后的比较规则 |
|---|---|
| required formulas / must-cover 总量 | 作为任务集合与分母，不标越少/越多越好 |
| raw accepted pages/invocations | 受分页策略影响，默认 direction=unknown |
| provider sends / tokens | 只有同 scope、有效交付、覆盖不退化时才解释为效率差异 |
| explicit gaps | 少报 gap 不等于变好；结合固定目标集的真实 resolved/unresolved 状态 |
| first-attempt acceptance | 保留，但同时给 required occurrence coverage 和 final-bound 结果 |
| supported/consumed 比率 | 分母必须是同一冻结 obligation 集合；报告集合差异 |
| 未测维度 | 不生成 delta；两侧未测原因都保留，不能后者覆盖前者 |
| 叙事连贯性/忠实性 | 由指定人工或盲评协议测量，未测则明确 not_measured |

`formula.required` 的减少、空 candidate 的零 token、提前失败的少调用、隐藏 gap 都必须有负例，保证不会被标成质量改善。

## 14. 历史目录迁移与授权执行流程

### 14.1 事故归档只读，不做恢复实验场

保留原始 archive、attempt-0001..0004、身份、旧 plan/manifest 和 stdout/stderr。诊断输出写在新的审计目录。禁止：

```text
删除/清空 invocation ledger
把旧 accepted 数改成 1
重写旧 identity 的 engine/validator/plan 字段
给旧页手动增加 max_attempts
把 Writer manifest 覆盖到 Formalizer 无后缀文件
将新失败日志混入历史 attempt 编号，伪装成原执行续跑
```

### 14.2 三种执行方式

| 意图 | 使用方式 | 允许复用 | 不允许继承 |
|---|---|---|---|
| 验证新引擎修复 | 新目录 `new`，或明确导入 Research 的 `fork_authoring` | 经过校验的冻结 Research | 旧 Writer 预算和 accepted 状态 |
| 同代码、同材料、同规则恢复未完执行 | 同目录 `resume`，通过 A/B 准入 | 同契约已验证响应/回执 | 修改身份后冒充兼容 |
| 对历史模型响应做本地重验 | 新 validation replay 结果 | 原始 response 字节及引用 | 把新验收结论改写为旧历史事实 |

目标源代码、作者输入、规则或有效配置不兼容时，应明确拒绝原地恢复。引擎修复后再运行可以建立新执行，但要在质量对照中记录这不是旧 run 自己恢复成功。

### 14.3 沙箱与命令授权

用户环境是每条命令独立 bwrap，宿主 `/tmp` 不自动可见，PID 命名空间隔离；上一条命令的放宽不会成为下一条的权限。执行 agent 必须对每条确需出沙箱的命令单独申请授权，禁止把“曾获授权”当作后续授权，也不能以打包多项副作用规避审批。

本文不要求使用宿主 `/tmp`。优先在明确的、不会被 run-root 归一化误重定向的独立目录保存新执行；已修的 nested `artifacts/runs/...` 归一化仍应保留回归。准备阶段也可能涉及 Formalizer 或辅助模型调用，不能因参数叫 `prepare` 就认定零成本。[S24] [S28]

### 14.5 Live 分三层，不直接全量盲跑

**L1：冻结证据、最小写作案例。** 在新执行中测试一个有完整材料的 grounded 段落和一个无 atom 的作者语义段落，再加一个明确需要局部 repair 的案例。记录真实 request/response、token provenance、各阶段接受结果与最终正文。不要把 only-prepare 当成 L1 完成。

**L3：跨项目验证。** 选择至少一个不同结构/公式密度的任务，避免把 EBCAR 阈值和组织模式当作系统性修复。已有 DyG-Mamba 等冻结材料只有在实际可访问、身份和授权均确认后才进入执行，不从历史记忆猜路径。

## 15. 可观测性：每次失败能回答的六个问题

不新增一个独立 dashboard 工程；扩充现有 run summary、doctor 和质量报告即可。

| 问题 | 所需最小信息 |
|---|---|
| 这是不是新修复的真实验证？ | engine/source/config/validator identity、run origin、new/resume/fork、导入来源 |
| 本页实际要求写什么？ | 最终 paragraph IDs/order、局部 reader goals、required occurrence 集合、权限、输出限制 |
| 为什么没有写出来？ | 材料缺失、投影丢失、归属不明、生成失败、绑定失败、传输失败等 typed owner |
| 这次到底有没有请求模型？ | event/send/response/acceptance 状态、usage provenance、未知预留 |
| 下游为什么没运行？ | 最早阻断阶段、直接依赖、剩余预算，不只报最后 acceptance_count |
| 修复是否真的提高质量？ | 相同任务集合、有效交付 scope、最终绑定覆盖、叙事评价与成本条件 |

### 15.1 信息通路审计字段

对 required 内容单元记录如下映射，不要求把它们全部塞给模型：

```text
author story / obligation
  → code evidence IDs / source spans / conditions
  → mechanism detail
  → authoring unit / narrative paragraph
  → physical page / invocation
  → exact request field
  → accepted paragraph span / formula occurrence
  → final-bound result / publication disposition
```

对某个信息点没有进入正文的情况，给出一个明确 disposition：未找到证据、研究未完成、超出作者范围、仅 review、被合法合并、需要 replan、生成未满足或最终验证拒绝。禁止仅用“字段不见了”表示过滤完成。

### 15.2 输出产物与状态分离

candidate、repository-verified、review/annotated 和 blocked diagnostic 不能共用一个含糊的“成功”标志。没有完整 clean candidate 时，可以保留失败的局部响应用于诊断，但不能混入正式正文，也不能拿它与另一份完整 Method 做总质量排名。

导出的证据包需避免 API keys、认证 header 和其他凭据；可保留请求结构、内容摘要和脱敏的 provider diagnostics。不能通过脱敏改写旧原始产物后再宣称字节未变；原始保留、导出副本单独登记。

## 16. 完成定义与禁止性验收

### 16.1 “代码修复完成”

A–F 的关键反例通过；修改点不是孤立 helper；生产调用路径有行为测试证明；全部已有离线测试无意外退化；新 schema/身份语义迁移清楚；旧归档字节保持不变。身份字段语义改变时要给出明确版本标记，旧 V2 不得被假装成新语义的兼容输入。

### 16.2 “恢复机制完成”

崩溃矩阵通过，预算和 ledger 口径一致，未知发送不重复调用，已收到响应能本地继续，fork 能按相同 birth metadata 恢复，所有入口给出同一主因。单纯“新目录跑通”不等于恢复机制已验证。

### 16.3 “质量改善得到证据”

L1/L2/L3 的实际 scope 和结果均有记录；required 义务集合不被删减；最终正文通过既有事实/权限/公式约束；连贯性、完整性和可发表性通过指定盲评/人工核对。效率仅在交付与覆盖不退化前提下比较。

### 16.4 下列结果不能作为完成证据

```text
只有新增模块和单元测试，没有生产接线
只有 pytest 总数，没有测试范围/当前 engine 绑定
只有 provider=NONE + write_method_text=False 的 smoke
只有 prepare 产物，没有 Writer/Binder/正文交付
只看到“6 段上限”，没有核对真实 request 中的全部段落
只看到 index 存在，没有复核消费字节和 upstream
只看到 accepted=true，没有对应 request/response/validator 绑定
只看到更少 tokens，没有同任务集合与有效交付条件
只在删除旧 ledger 后成功
```
