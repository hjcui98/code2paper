5. LaTeX parser/representation check 只检查括号、环境、未定义 symbol 等格式；不得由 harness 发明数学
   内容来“修复”公式。
6. `code_verified` 公式及解释在句级/公式级验证通过后可进入 Candidate 和 Verified。
7. `author_intent` 或 `partial` 公式可进入 Candidate，并以自然的段落级 caveat/review 关联呈现；在未
   获代码/形式化支持前不得进入 Verified。
8. `paper_code_mismatch` 同时保存作者期望公式和仓库实际证据差异，不允许默默选择一边。
9. Cross-section Editor 统一符号、上下标和首次定义位置；任何改变运算语义的 patch 必须拒绝并回到
   Formalizer，而不是由 Editor 自由改公式。

#### 19.6.5 Writer 可见形式

Writer 不需要看到 equation/fact/claim ID。每节只收到：

- 公式的 reader-facing purpose；
- 已授权 LaTeX；
- 符号定义；
- 可陈述的解释；
- 必须保留的 material condition；
- authority/caveat lane。

Writer 负责把公式放进论证段落，Formalizer 负责公式和解释的内容来源，Editor 负责全篇一致性。

#### 19.6.6 聚焦回归

扩展 `tests/test_agentic_formalization_guards.py`、
`tests/test_agentic_publication_method_writer.py`、
`tests/test_agentic_writer_paper_language_quality.py`，至少证明：

- section 只收到与其 proposition 绑定的 equation；
- core code equation 生成非空 LaTeX、符号定义和 prose explanation；
- 未授权 operator/constant/dimension 仍被拒；
- author-intent formula 留在 Candidate、带 review、不会进入 Verified；
- paper/code mismatch 两侧均保留且不会伪装 verified；
- defensive branch 不生成公式；
- Editor 只做符号一致性修复，不能改变运算；
- equation 可用但 Formalizer 空返回时产生 typed unresolved，不静默完成。

### 19.7 Q3 — Writer/Editor 从“代码事实串”升级为论文论证

#### 19.7.1 Writer prompt 收缩为四层

保留现有 WriterView 和内部 ID 隐藏，模型可见输入固定为：

1. **本节要回答什么**：story node、section purpose、与前后节关系；
2. **可正向陈述的 Method propositions**：只含 `method_positive` 和满足条件的
   `method_conditional`；
3. **必须显式 caveat 的作者意图/partial/mismatch propositions**：提供自然的论文级表达目标和
   review linkage，不给模型协议术语；
4. **不得改变的条件、数字、配置和公式**：reader-facing meaning、LaTeX 和符号定义。

fact ID、claim ID、concept key、source span、semantic frame 和 validator vocabulary 留在 binding
sidecar，只用于响应校验和追溯。

#### 19.7.2 Writer 行为

1. 先围绕 section question 和 author story 写核心机制，再用代码证据补充具体实现关系；不得按仓库
   文件或调用顺序组织正文。
2. 每节必须有实质正文，不能用 `We aim to explain...`、`Pending confirmation...` 或只有标题的占位
   代替内容。证据不足时也要基于 author intent 写成明确、自然的 candidate narrative，并生成 review
   item；不能只留下协议提示。
3. 论文正文默认不出现 `self.*`、字典索引、`.shape[...]`、函数调用链、内部 ID、`author_intent` 等
   生产协议词。若一个低层 binding 对读者无科学意义，直接不写，而不是强迫模型把代码放入括号。
4. 一个典型 section 应自然形成“问题/目的 -> 机制 -> 必要的数学形式 -> 实现与机制关系 -> 输出或
   下一节过渡”的若干段落；不要求所有节套同一模板，也不以字数堆积代替内容。
5. 对同一 caveat 在一个段落或小节层面说明一次，不在每句重复免责声明。
6. Writer 可以省略 audit-only 事实，但不能省略被 Architect 选为本节核心的 supported proposition；
   若无法表达，返回 typed writing issue/callback，而不是生成空壳。
7. Formula package 存在时必须在相应机制附近渲染并解释；不能把公式列表堆在节尾，也不能只写符号
   而无文字含义。

#### 19.7.3 Editor 行为

Cross-section Editor 的优先级改为：

1. 作者 story spine 和章节问题是否连贯；
2. 核心机制是否先于低层实现细节；
3. 同一术语/符号/对象全篇是否一致；
4. 公式是否在首次使用前后得到定义和解释；
5. 是否有重复段落、模板句、过密 caveat、代码流水账和无意义支线；
6. 段落边界、过渡和标题完整性。

Editor 可重排或合并本节段落、消除重复和统一术语，但不能新增事实、改数字/公式语义或删除仍需
保留的 author-intent/mismatch 内容。任何不安全 patch 被拒后保留 incumbent Candidate。

#### 19.7.4 原文对照只作为质量评估

生产逻辑不得硬编码三个项目；原文只作为 author-intent/质量参照。冻结批次的人类/Codex 审核至少
检查：

- EBCAR：主线集中在 reranking、augmentation、hybrid attention、InfoNCE 和 inference；空 loss、
  shape、ingestion、chunk bookkeeping 不应成为正文主线；
- LinearRAG：保持 Tri-Graph -> local bridging -> PPR，并补足已有证据支持的激活、稀疏传播、
  pruning/stopping、初始化/score 与核心公式；
- DyG-Mamba：四通道输入、`Delta t`、`A/B/C`、约束和 downstream head 成为主线；padding、routing、
  edge-memory 只有在作者故事选择且证据充分时才出现。

#### 19.7.5 聚焦回归

扩展现有 Writer、section-writer、repair 和 publication tests，证明：

- 同一 evidence 在不同 author story 下按不同组织写作；
- Writer payload 只有上述四层，无内部 ID 和 audit-only fact；
- candidate-only section 生成有内容的 caveated narrative，而非占位句；
- core proposition 遗漏进入 repair/callback，低层 audit fact 遗漏不算 coverage failure；
- raw code-trace、模板句、重复 caveat 和空节成为 Editor/Rewrite issue；
- Editor 改善段落和术语但不能改变公式/事实；失败 patch 保留 incumbent；
- Formula package 被实际渲染并在正文解释。

### 19.8 Q4 — 灵活但有上限的 Writer/Editor/Rewrite/callback 循环

当前循环方向正确，不再另建一个 verifier 写文章。Verifier 负责发现并结构化问题，Writer、Formalizer、
Editor、Rewrite 是内容 owner。改动目标是让循环根据剩余问题和增益自主决定是否继续，而不是固定只
调用一次，也不是无限重试。

#### 19.8.1 调度规则

1. 增加一个统一可配置的 section revision budget：默认最多 3 个内容修订 round，配置可提高，但产品
   hard cap 为 5；callback 工具调用继续受独立 tool-turn budget 约束。
2. 每轮由现有编排器根据 typed issues 选择 owner：
   - 缺仓库/配置事实 -> Research callback；
   - 核心公式/符号缺失 -> Formalizer；
   - section 内容缺失或论证失焦 -> Writer；
   - 跨节顺序、重复、术语、符号一致性 -> Editor；
   - 局部措辞、qualifier、代码痕迹、格式 -> Rewrite；
   - author/literature/formalization 外部问题 -> review queue，不伪造答案。
3. 一个 round 可以包含必要的多次 repository tool call；Agent 根据新 observation 决定下一次查询，
   直到问题被回答、预算耗尽或连续无 information gain。不得把 callback 固定为“一次查询”。
4. 每轮后比较目标 issue、核心 proposition coverage、公式 disposition 和文档完整性。只有目标改善且
   无关键回归才提交；否则保持 incumbent。
5. 连续一个完整 round 无语义增益，或达到 budget，即停止自动修复并发布
   `review_ready_with_warnings`。停止不是失败，不再为幸运采样重跑相同输入。
6. audit-only qualifier/style 问题不得触发 callback 或重复 Rewrite。
7. 若 callback 新事实改变 proposition、formula 或 story placement，只失效并恢复受影响 section；未受
   影响 section 保持 checkpoint 和正文不变。

#### 19.8.2 Warning 和 Verified 处理

Candidate findings 均为可排序 warning/repair request：

- critical：unsupported implementation positive、material condition/number/formula mismatch、
  paper/code contradiction；
- major：核心 story/proposition/公式缺失、章节失焦、严重重复或不可编辑结构；
- minor：术语、过渡、句式、局部密度和轻微格式。

warning 严重度决定修复优先级和 `publication_ready`，不决定 Candidate 是否存在。任何仍有 factual
warning 的句子都从 Verified 排除，并在 review sidecar 中保留 section、原句、原因、所需证据和建议
动作。

#### 19.8.3 聚焦回归

- LLM/编排器可在第一轮有增益后选择第二轮，并在问题解决后提前停止；
- 达到 hard cap 或 no-progress 后返回最佳 Candidate 和 warnings；
- callback 连续调用两个不同 repository tools 后补齐证据并只恢复受影响节；
- Formalizer/Writer/Editor/Rewrite owner routing 正确；
- audit-only 问题不消耗修复预算；
- 任意后续调用失败都不丢失之前的 Candidate checkpoint。

### 19.9 Q5 — 报告、兼容和产品出口

1. `publication_writer_result_v1.json`、`method_draft_bundle_v1.json`、quality report、runner summary、
   readiness 和 completion report 统一读取 Q0 的独立状态字段。
2. 保留旧状态字段的兼容输出和明确映射期；任何消费者不得仅因
   `candidate_validation_status=warnings/error` 推导 `candidate_available=false`。
3. `repository_verified_method.md` 由句级 verdict 白名单构建：只有 supported 且所有 material
   conditions/numbers/formulas 通过的句子进入。过滤发生在 Verified projection，不修改 Candidate。
4. `author_review_candidates.json` 同时承接：author-intent、partial、mismatch、外部待证、未解决
   factual warning 和 Formalizer typed disposition；每项保留非空 proposed body/question/needed
   evidence，并绑定对应 section。
5. 现有执行记录继续保存命令、代码状态和 runtime identity，但本轮不为增加 digest、台账字段或测试
   数量做额外开发。它们只证明运行绑定，不代表文字质量。
6. 旧 R8 路线只做兼容回归，不把这次 Candidate-first 状态变化反向扩展成新的 R8 acceptance 门。

### 19.11 一次冻结 authoring 实测

静态里程碑通过后，在同一最终代码状态上运行 DyG-Mamba、LinearRAG、EBCAR 三个 fresh frozen-
authoring replay。遵循 runtime preflight：`/health`、`/v1/models`、模型身份、running/waiting、KV-cache、
fresh `/tmp` 输出根均需记录。

三项目彼此独立，runtime capacity 足够时可最多三并发；若 waiting 持续、KV-cache 压力或 abort/OOM
出现，立即降到二并发或串行。不要在同一输出根写入，也不要在不变代码上额外重跑更差/更好样本。

每个项目必须检查：

1. Candidate 非空、章节和 plan 一致、即使有 critical warning 也被发布；
2. Candidate/Verified/warnings/publication-ready 四种状态在 summary 中独立；
3. Verified 只含 supported 句，0 unresolved factual leakage；
4. `audit_only` 事实仍可在 evidence 中找到，但不进入默认 Writer proposition/coverage；
5. material conditional 缺失时 warning 和 Verified exclusion 都真实发生；
6. 有核心 equation evidence 的 section 出现至少一个已接受 Formula package，或有明确 typed
   disposition；正文实际渲染 LaTeX 并解释符号，不能只看 artifact 数量；
7. callback/rewrite 只恢复受影响 section，且任何 no-progress 都保留 incumbent；
8. 原文对照的主线检查达到 19.7.4 的项目级目标。

不以 Candidate zero-warning 为验收条件。质量审核关注它是否已经是“可以交给作者继续改”的 Method：
核心故事可识别、每节有实质内容、公式覆盖关键机制、没有大段代码流水账或模板占位、warning 可定位且
Verified 边界诚实。

### 19.12 本轮验收标准

#### 19.12.1 必须通过

- 任一非空 Writer 输出都形成 durable Candidate；后续失败不能删除或替换为空稿；
- Candidate warnings 不再造成 product blocked 或输出缺失；
- Verified 保持 fail-closed，未解决 factual warning 的句子不进入；
- EBCAR 的 augmentation/concatenation 不再继承 empty-loss guard，empty-loss 仍留在 audit evidence；
- audit-only 事实不再成为 Writer obligation、recall 分母或 qualifier repair 触发器；
- final qualifier 按精确 selected proposition 绑定，不使用 obligation-wide/fuzzy union；
- Formalizer 对核心公式产生 section-scoped LaTeX、符号定义、解释和 authority disposition，或诚实
  typed unresolved；
- Writer/Editor 输出按 author story 组织，核心机制优先于代码操作，candidate-only 内容是自然的
  caveated prose 而非占位；
- 修复循环可多轮但有上限、基于增益停止，并始终回落到 best Candidate；
- 三项目 fresh batch 同一代码状态完成，产物和报告自洽。

#### 19.12.2 可以诚实保留

- Candidate 仍有 critical/major/minor warnings；
- `publication_ready=false`；
- 某些 author-intent 公式或机制只存在于 Candidate/review；
- Verified 比 Candidate 短或缺少整节；
- 本地模型文字仍非投稿终稿；
- research/autonomy 仍是 degraded/incomplete，只要不被改名为完成。

#### 19.12.3 失败条件

- 因 warning、validator error 或修复耗尽导致已有 Candidate 消失；
- 为得到零 unsupported 而删减 Candidate、降低 Verified 证据要求或缩小应写的核心 Method；
- packet guard 继续污染无关事实；
- Formalizer 继续在存在核心 equations 时无结果且无 typed disposition；
- Writer 仍主要输出代码调用、shape/index/guard 流水账或空壳段落；
- 用重复不变 live run 选择幸运样本，或在生产逻辑硬编码三个项目；
- 用更多 hashes、contracts、测试文件或台账代替文本质量改善。

### 19.13 实施返回要求

实现 Agent 完成后只更新一次 `.agent/implementation.md`，包含：

- Q0--Q5 每包的根因、实际改动文件和行为变化；
- Candidate 状态解耦前后示例，以及失败后仍保留 checkpoint 的证据；
- exact guard ownership 的最小纵向 fixture 和 EBCAR 冻结证据对比；
- `method_positive / method_conditional / audit_only` 数量及其 Writer/coverage 去向；
- 每项目 Formula package、正文实际 LaTeX 和 authority status；
- Writer/Editor/Rewrite/callback 调用轮次、增益、停止原因和 incumbent preservation；
- 聚焦/全量静态命令、退出码和摘要；
- 三个 fresh replay 根、runtime pre/post、独立状态、Candidate/Verified/warning/quality 汇总；
- 对原文主线的逐项目简短质量审计，而不是只报告字节数和测试数；
- 剩余问题属于代码、prompt、证据、作者确认还是本地模型质量的明确归属。

完成后返回 Codex 做只读验收；Codex 不重跑测试或 API。下一轮验收首先阅读最终 Candidate、
Formula package、warnings 和 Verified，而不是先看哈希或通过数。
