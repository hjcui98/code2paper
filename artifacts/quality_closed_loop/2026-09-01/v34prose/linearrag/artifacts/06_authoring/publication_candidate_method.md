## Motivation: revisit GraphRAG shortcomings from relation extraction errors

The Tri-Graph is a hierarchical graph whose node layers—entities, sentences, and passages—interconnect through sparse contain and message adjacency, anchoring the entire retrieval pipeline while avoiding explicit relation extraction. Its sparse adjacency structure replaces the dense relation triples that standard GraphRAG pipelines must extract, reducing the error surface that propagates through downstream retrieval. The retrieval path activates under the condition (`self.config.use_vectorized_retrieval`) that precomputes sparse adjacency matrices for vectorized retrieval.

## LinearRAG overview: Tri‑Graph concept and two‑stage retrieval philosophy

LinearRAG constructs an offline Tri‑Graph whose node sets comprise entities, sentences, and passages, with edge sets encoding containment and message adjacency relations among these nodes. The precise algebraic form of the containment and message adjacency matrices is not yet fixed within the current specification.

## Offline Tri‑Graph construction

The offline construction phase assembles a Tri-Graph by splitting each passage into sentences, extracting entities with spaCy, and populating two sparse adjacency structures: a contain matrix linking passages to their constituent entities and a mention matrix linking sentences to entities they reference. The pipeline is gated by a non-empty passage check (`len(new_passage_hash_ids) > 0`), after which `LinearRAG.index` invokes `self.extract_nodes_and_edges` to return entity nodes, sentence nodes, and the passage-to-entity mapping.

## First retrieval stage: relevant entity activation via local semantic bridging

Entity activation in the first retrieval stage proceeds through local semantic bridging: for a query, relevant entities are initialized from matched seed entities, query–sentence similarities are computed, and scores are iteratively propagated through the sentence–entity subgraph, discovering latent intermediate entities that support multi-hop connections. During propagation, dynamic pruning applies a threshold-based filter that retains only strongly relevant entities, preventing combinatorial expansion and noise. Concretely, `graph_search_with_seed_entities` invokes `calculate_entity_scores_vectorized` with the question embedding, seed entity indices, seed entities, seed entity hash IDs, and seed entity scores to produce entity weights and the set of activated entities; it then combines entity weights with passage weights to yield node weights, which are propagated via personalized PageRank over the graph (directed=False, implementation='prpack', damping configured by `self.config.damping`) and sorted to return `(ppr_sorted_passage_indices, ppr_sorted_passage_scores)`. Entity activation is gated by the condition that the entity label is ordinal or cardinal and that the entity text is absent from the sentence-to-entities index (`ent.label_ == 'ORDINAL' or ent.label_ == 'CARDINAL'`, `ent_text not in sentence_to_entities[sent_text]`); the vectorized branch is further conditioned on `self.config.use_vectorized_retrieval`, whose activation value is not yet established in the current configuration state.

## Second retrieval stage: passage retrieval via global importance aggregation

Passage retrieval in the second stage proceeds by personalized PageRank over the passage–entity subgraph, using activated entities as seed nodes and initializing passage nodes with a hybrid score that combines direct query–passage similarity with entity-based statistics such as occurrence and level (`self.config.use_vectorized_retrieval`). The hybrid initialization assigns each passage node a starting importance that reflects both its textual relevance to the query and its structural role in the entity graph, allowing influence to propagate through entity–passage edges during the PageRank computation. The resulting PageRank scores rank passages globally, yielding a sorted list of passage indices and their corresponding importance scores as the retrieval output.
